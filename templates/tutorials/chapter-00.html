1. 开发环境配置

1.1 JDK 25

JDK 包含 Java 运行环境和 javac 等开发工具。本教程使用 JDK 25；安装时请选择 JDK，而非仅包含运行环境的 JRE。

下载 Eclipse Temurin JDK 25

下载与操作系统、处理器架构匹配的安装包：常见 Windows 电脑通常选择 x64，Apple Silicon Mac 选择 aarch64。安装后重新打开终端，执行以下命令，确认 java 和 javac 的主版本均为 25。

java -version
javac -version

如果 java 和 javac 版本不同，先检查 PATH 与 JAVA_HOME。JAVA_HOME 指向 JDK 的根目录，不是它下面的 bin 文件夹。改完后重新打开终端再试。

1.3 Fabric Mod Template

打开 Fabric 官方模板生成器

选择 Minecraft 26.3，填好模组名称、Mod ID 和包名。我这里用 Vocabulary Spark、vocabulary-spark 作为例子；包名换成你自己的，例如 io.github.piscescup.vocabularyspark。Mod ID 是资源命名空间，尽量在一开始就确定下来。

选择 Java，并按需启用客户端源码分离和数据生成。下载、解压后，在 IDEA 中使用 Open 打开包含 settings.gradle、build.gradle 和 gradlew 的项目根目录，等待首次 Gradle 同步完成。

同步成功后，在项目根目录的终端启动开发客户端。Windows PowerShell 用第一条，macOS / Linux 用第二条；它们是两种系统的写法，不是要依次执行。

# Windows PowerShell
.\gradlew.bat runClient

# macOS / Linux
./gradlew runClient

开发客户端正常启动后，环境配置完成。若启动失败，查看 Build 或终端中的报错，检查 JDK 配置与依赖同步状态。

4. 项目文件介绍

Gradle 配置负责构建流程与依赖管理，Fabric 配置负责模组描述与加载入口。以下按 Minecraft 26.3 模板介绍主要文件。

4.1 Gradle：构建和依赖

文件或目录用途
build.gradle构建脚本。声明 Loom、Minecraft、Fabric Loader / API 等依赖，以及编译和资源处理规则。26.3 官方模板使用 net.fabricmc.fabric-loom，不要直接套旧模板的插件名和 modImplementation 写法。
gradle.properties集中放版本与项目属性。当前模板使用 minecraft_version、loader_version、fabric_api_version、version 和 group 等键；旧教程的 mod_version、maven_group 不一定适用于这一份脚本。
settings.gradle定义项目名称、插件解析仓库等设置。
gradle/wrapper/gradle-wrapper.properties指定本项目使用的 Gradle 发行版。优先使用项目的 Wrapper，无须额外安装一个全局 Gradle 来替代它。
gradlew / gradlew.batGradle Wrapper 的启动脚本。前者用于 macOS / Linux，后者用于 Windows。
.gradle/ · build/分别保存本地构建缓存与输出。它们不是主要源码目录，也不应该把每次构建产生的文件当成手写代码提交。

4.2 Fabric：入口、资源和模组信息

位置用途
src/main/java/放通用 Java 代码，包括实现 ModInitializer 的入口类。这里的代码可能同时用于客户端和独立服务端，别把只存在于客户端的渲染类随手放进来。
src/client/java/启用客户端源码分离时放客户端专用代码，通常包含 ClientModInitializer。是否存在这个目录取决于生成模板时的选项。
src/main/resources/fabric.mod.json模组的描述文件。重点看 id、name、version、environment、entrypoints、depends 和 mixins。入口类改名或搬包后，也要检查这里的全限定类名。
assets/vocabulary-spark/客户端资源的命名空间目录，一般位于 resources 下，放语言、贴图等资源。这里的 vocabulary-spark 要与 Mod ID 对上。
data/vocabulary-spark/服务端数据的命名空间目录，例如配方、战利品表等。随着后面增加内容再创建，不需要在这一章把所有子目录都搭完。
*.mixins.json列出 Mixin 类与相关配置。客户端配置也可能位于 src/client/resources。暂时不写 Mixin 时，先知道入口在这里即可。
src/main/generated/启用并配置数据生成后可能出现的输出目录，不是每份基础模板都自带。通常修改生成器再重新生成，不要把它当主要手写目录。

特别留意 Mod ID 与 Java 包名的区别：vocabulary-spark 可以做 Mod ID，但 Java 包名不能带连字符。包名可以写成 vocabularyspark，资源路径仍然使用 vocabulary-spark。

我习惯将 Mod ID、模组元数据、日志和常用工具方法集中放在 References 类中，方便统一维护。小型项目也可以将这些内容保留在入口类中。

5.2 字段与方法说明

字段或方法用途
MOD_ID唯一的模组标识，也是资源的命名空间。建议只在一处定义，别在整个项目里重复写字符串。
FABRIC_LOADERFabric Loader 的实例，供后续查询已经发现的模组信息。
VOCABULARY_SPARK_MOD用 Mod ID 找到对应的 ModContainer。这里用 orElseThrow() 明确表示：找不到自己的模组就直接失败，先检查 ID 是否一致。
VOCABULARY_SPARK_METADATA模组的元数据入口；MOD_NAME 和 MOD_VERSION 从这里读取，避免另外维护一份名字或版本。
GSON共享的 JSON 工具。setPrettyPrinting() 让输出便于阅读；disableHtmlEscaping() 保留部分 HTML 字符原样，但不代表可以直接把 JSON 当 HTML 插入网页。
MOD_LOGGER以模组名称创建的 Log4j 日志器。这里的 Logger 必须导入 Log4j 的类型，不能误选成 org.slf4j.Logger。
fromPath(path)自动补上本模组的命名空间，少重复写 MOD_ID。传入的只是路径，不包含 vocabulary-spark: 这样的前缀。

创建贴图资源标识的示例：

Identifier texture = VocabularySparkModReferences
        .fromPath("textures/gui/dictionary.png");
// vocabulary-spark:textures/gui/dictionary.png

5.3 静态初始化

这个类里的元数据字段，会在类首次初始化时按顺序执行。即使只调用 fromPath()，也会先查询 ModContainer。因此它适合放在 Fabric 已经准备好模组信息的初始化流程中使用，不要把它拿到没有 Fabric 环境的普通 main() 里直接测试。

MOD_ID 是编译期字符串常量，单独读取它通常不会触发类初始化；这和读取 MOD_NAME、MOD_VERSION 等运行时字段不同。以后若想让资源 ID 工具完全独立，可以把 fromPath() 与读取元数据的部分拆开。
